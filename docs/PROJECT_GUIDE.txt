==============================================================================
A1. 一句话定位
==============================================================================

这是一个「以作业（Job）为中心」的视觉 AI runtime：把昂贵、易失败的 VLM 推理
放进可恢复、可观测、可评估的状态机里；Livehouse 演出选片是真实业务负载，
不是抽象框架 demo。

核心卖点不是「调用视觉模型打分」，而是：
  Durable Jobs + Bounded Inference + Model Fallback + End-to-end Observability


==============================================================================
A2. 解决什么真实问题
==============================================================================

一场 Livehouse 会留下大量相似照片（预览 JPEG + 旁路 RAW）。脚本能跑通处理，
但通常很难回答：

  1) 任务跑到哪一步了？
  2) Worker 崩溃后如何恢复，会不会重复执行？
  3) 模型为什么变慢 / 超时？主模型挂了有没有降级？
  4) 成本花在哪几次 VLM 调用上？
  5) 筛选质量相对人工标注如何？门控是否真的省调用？

本项目把流水线挂在持久作业系统上：SQL 是执行事实（SSOT），Celery 只传递
job_id；Gallery / Infra Console 形成「提交 → 观测 → 确认导出」闭环。

A5. 主路径（必须先背熟）
==============================================================================

线性主路径（面试 / 排障都从这里讲）：

  ingest (Go SD/brain → sessions/photos)
    → POST /api/ingest/check_new_images
    → tasks.process_brain_ingested          # 播种 ANALYZE_SESSION jobs
    → tasks.run_job(job_id)                 # Celery 只带 job_id
    → services.job_executor.JobExecutor     # 原子 claim → run → finalize
    → PipelineStageRunner
         PREPARE_INPUT
         → STAGE1_FILTER          # OpenCV 廉价门控
         → STAGE2_FAST_SCORE      # 快速美学分
         → STAGE3_VLM             # 有界推理队列
         → WRITE_ARTIFACT / FINALIZE
    → PrioritizedInferenceQueue + router    # primary → fallback
    → artifacts: analysis_results.json, job_events, model_runs

关键原则：
  · Celery AsyncResult 不是权威；SQLite jobs 行才是。
  · claim 用 BEGIN IMMEDIATE + 条件更新；重复投递第二次 claim 失败即 skip。
  · 推理有并发上限与队列背压，禁止对 Ollama 无界并行。
  · 每次模型 attempt 写入 ledger，供 Infra 归因。


流水线阶段常量见 services/pipeline_stages.py：

  PREPARE_INPUT → STAGE1_FILTER → STAGE2_FAST_SCORE → STAGE3_VLM
  → WRITE_ARTIFACT → FINALIZE


作业状态机（概念）：

  QUEUED / FAILED_RETRYABLE
    → CLAIMED
    → PREPROCESSING → INFERENCING → (POSTPROCESSING) → SUCCEEDED
  失败可：FAILED_RETRYABLE →（耗尽）DEAD_LETTERED
  或：FAILED_PERMANENT / CANCELLED

  Worker 崩溃：心跳 + claimed_at 过期 → requeue；旧 claim_generation 的终态
  写入会被 ClaimFenceError 挡住（防僵尸覆盖）。

==============================================================================
A9. 推理与背压（为什么这是「runtime」而不是脚本）
==============================================================================

PrioritizedInferenceQueue（inference/queue.py 等）：
  · 限制 inflight / 队列长度
  · 排队过久可触发 fallback_model 或错误
  · 按 (namespace, project_key) 可选小时配额（默认关）

Router：
  · primary → fallback；每次 attempt 记入 model_runs
  · 支持 Ollama / vLLM / OpenAI-compatible / mock

已知边界（面试要主动说）：
  · 背压主要是进程内，不是集群 GPU 配额
  · Cancel 改 SSOT，不保证立刻掐断已在飞的 HTTP
  · SQLite 单节点 SSOT，不是多活集群库

A11. 评估与质量契约
==============================================================================

固定集：约 250 张人工标注（data/eval/）
UI：/eval ；报告索引 reports/eval/meta.json

典型 Recorded 数字（以报告为准，勿臆造）：
  Stage3 vs 人工：Spearman≈0.36, MAE≈6.09, P@20≈0.55
  两阶段门控：admitted Spearman≈0.52，VLM 调用约 6.4%（相对全量）
  Agent stratified (budget 40)：sel.P≈0.43 — 略优于 greedy heuristic

Provenance 标签（展示任何数字前先贴标签）：
  Live | Recorded Run | Simulated | Showcase Fixture

质量平台契约（quality/CONTRACTS.md）：
  content_hash / file_key / item_id 连接键冻结
  overall 0–100；dims 0–10；keep bool
  新评估代码禁止另起一套 join key 或分数刻度


常用命令：

  python scripts/eval_stage3.py run --labels data/eval/labels.jsonl \
      --predictions data/eval/images/analysis_results.json
  python scripts/eval/eval_two_stage_gating.py --out reports/eval/two_stage_gating.json
  python scripts/eval/eval_agent_selection.py ... --budget 40


==============================================================================
A12. 平台边界与 Batch E（hooks ≠ cutover）
==============================================================================

今天是什么：
  单节点 job-centric AI runtime；namespace/project_key 是软标签过滤。

今天不是什么：
  多租户硬隔离 / Infra Console 的完整 RBAC·OIDC /
  多写集群数据库 / 集群级公平配额。

Batch E 已落地脚手架（见 docs/PLATFORM_SCOPE.txt）：
  · LIVEHOUSE_BRAIN_BACKEND=postgres → NotImplementedError（防假 Postgres）
  · artifacts.content_digest（本地 SHA-256，为对象存储 CAS 准备）
  · 可选 per-scope VLM 小时配额
  · 可选 OTEL bootstrap
  · HTTP 安全：非 loopback 默认 fail-closed；本地可用 ALLOW_INSECURE_LOCAL

真正 cutover 仍需：Postgres + 对象存储 + 集群配额 + 鉴权隔离。

------------------------------------------------------------------------------
B2. 后端系统与作业编排  ★★（本项目灵魂）
------------------------------------------------------------------------------

必须建立的心智模型：
  「消息队列通知」≠「执行事实源」
  Celery 传 job_id；SQLite 事务 claim 才算开工。

建议补齐的概念：
  · 状态机：幂等、CAS（compare-and-swap）、generation / fencing
  · At-least-once 投递 + 幂等消费者
  · Retry vs dead-letter；stuck requeue；cancel 语义边界
  · Worker capacity / admission control
  · Celery + Redis：broker、worker、beat 各自职责
  · FastAPI：路由拆分、依赖注入直觉、同步 vs 异步边界
  · SQLite：BEGIN IMMEDIATE、单写者、何时该迁 Postgres

推荐自学关键词：
  job queue design, claim-check-work, saga/outbox（了解即可）,
  backpressure, bulkhead, circuit breaker / fallback


------------------------------------------------------------------------------
B3. 计算机视觉与图像管线  ★～★★
------------------------------------------------------------------------------

Stage1 相关：
  · 图像表示（BGR/RGB、直方图）
  · 清晰度：Laplacian variance
  · 运动模糊：梯度方向不对称（Sobel）
  · 曝光 / 对比度启发式
  · EXIF 方向与预览 JPEG vs RAW 配对

Stage2：
  · 「廉价美学分」作为召回/门控，而非最终裁判
  · Precision/Recall 权衡：砍候选 vs 漏掉 keeper

工程直觉：
  · I/O 与 decode 常是热点；优化要量再动
  · 预览图路径与归档目录约定（Previews + RAW/）


------------------------------------------------------------------------------
B4. 多模态模型与推理服务  ★★
------------------------------------------------------------------------------

概念：
  · VLM vs 纯文本 LLM；vision token / 上下文长度
  · 温度、max tokens、结构化输出（JSON schema 稳定性）
  · 本地推理：Ollama；连续批处理：vLLM；OpenAI-compatible API
  · 超时、重试、主备模型、降级质量（degraded success）
  · 队列等待时间 vs 纯推理 wall time（延迟拆解）

本仓库实践点：
  · 保持 Stage3 输出 schema 稳定（除非显式迁移）
  · agent_chat_model 与打分 VLM 分离
  · model_runs 账本按 attempt 记账（成本 / 失败归因）

C. 面试时可用的「诚实三边界」
==============================================================================

  1. SQLite 是执行 SSOT — 适合单机复现，不是多活集群库。
  2. 推理准入 / 背压主要在进程内 — 不是集群 GPU 配额。
  3. 单节点共享卷上的本地路径产物 — 不是对象存储多副本。

扩展实验（KEDA / Operator / RLHF / Agent 策展）可以讲，但不要和主路径抢镜头。
